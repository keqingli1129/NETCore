# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

`NZWalks.API` is a standalone .NET 10 REST API over a "New Zealand walks" domain — three
aggregates: **Regions**, **Walks**, and **Difficulties** (a `Walk` belongs to one `Region`
and one `Difficulty`). It is a single self-contained web project: no layering, no project
references, and no shared code with the rest of the repository.

It is a member of the root `NETCore.sln` but is otherwise **unrelated to the Clean
Architecture CoreMVC/CoreWebAPI solution** described in the repo-root `CLAUDE.md` — different
domain, different database (`MVCNet`), different (flat) design. Treat the two as separate
codebases that merely share a git repo and solution file.

## Commands

Run from the repo root (`NETCore/`) or from `NZWalks.API/`:

```bash
dotnet build ./NZWalks.API/NZWalks.API.csproj -c Release
dotnet run   --project ./NZWalks.API            # https profile → opens /scalar/v1
```

- Dev URLs: `https://localhost:7223` and `http://localhost:5062`. The launch browser opens
  the Scalar API reference at `/scalar/v1` (OpenAPI + Scalar are only mapped in Development).
- **There is no test project** for `NZWalks.API`.

## Data access (DB-first, scaffolded)

- The EF Core model is **database-first, scaffolded by EF Core Power Tools** from the
  `MVCNet` SQL Server database — see `efpt.config.json` (Fluent-API-only, `DateOnly`/`TimeOnly`).
  `Models/MVCNetNZWalksContext.cs`, `Models/Walk.cs`, `Models/Region.cs`, and
  `Models/Difficulty.cs` are marked `// <auto-generated>` with `#nullable disable`.
  **Do not hand-edit these** — re-scaffolding overwrites them. There are no EF migrations here.
- The **only** connection string actually used is `NZWalksConnectionString` (wired in
  `Program.cs`). The second entry (`MVCNetNZWalksContext`, a localdb string) is unused. The
  used string points at a machine-specific SQL Server Express instance — it is environment-specific.

## Request/response mapping

- Entities never cross the API boundary. **AutoMapper** (`Mappings/AutoMapperProfiles.cs`)
  maps entities ↔ DTOs; the profile is registered via `AddAutoMapper(typeof(Program))`.
- DTOs are **positional C# `record`s**, grouped one file per aggregate under `Models/DTOs/`.
  Each file holds the read DTO plus the `Add…RequestDto` / `Update…RequestDto` write records
  (e.g. `WalkDto.cs` contains `WalkDto`, `AddWalkRequestDto`, `UpdateWalkRequestDto`). When
  adding a field, update the record(s) **and** add the corresponding `CreateMap` line.

## Conventions and known inconsistencies

Be aware of these before extending the code — they are easy to trip over:

- **Two competing data-access styles coexist.** The CRUD controllers (`WalksController`,
  `RegionsController`, `DifficultiesController`) inject `MVCNetNZWalksContext` **directly** and
  do their own querying + mapping. Meanwhile `IWalkRepository`/`WalkRepository` implement a
  repository pattern and are **registered in DI but wired to no controller** — a half-finished
  refactor. Pick one approach deliberately for new work rather than assuming the repository is live.
- **Routes are pluralized controller names**, not the XML comments. `[Route("api/[controller]")]`
  yields `api/Walks`, `api/Regions`, `api/Difficulties` — even though the `// GET: api/Walk`
  comments say otherwise. Ignore those comments.
- **Leftover template/stub code**: `WeatherForecast.cs` + `WeatherForecastController.cs` (the
  project template) and `SudentsController` (misspelled; route `api/Sudents`) returning a hard-coded
  stub. The `NZWalks.API.http` file only exercises `/weatherforecast`. None of these represent the
  real domain.

## DI wiring (`Program.cs`)

`AddDbContext<MVCNetNZWalksContext>` (SQL Server) → `AddScoped<IWalkRepository, WalkRepository>`
→ `AddControllers` → `AddAutoMapper(typeof(Program))` → `AddOpenApi`. HTTPS redirection and
authorization middleware are present, but **no authentication is configured** (auth is a no-op).

## A sibling project pins a copy of this API's OpenAPI document

`NZWalks.MVC` generates its API client at build time from a **committed copy** of this API's
OpenAPI document, checked in at `NZWalks.MVC/OpenAPIs/nzwalks.v1.json` — it does not talk to a
running `NZWalks.API` during its build. If you rename a route, add/remove/rename a DTO property,
or otherwise change a Regions/Walks/Difficulties contract here, that copy goes stale: `NZWalks.MVC`
still builds cleanly and only fails at runtime (or silently drifts, e.g. a renamed DTO property
becomes a parse failure instead of a compile error). Re-capture it after such a change — see the
"Refreshing the API contract" section in `NZWalks.MVC/CLAUDE.md` for the exact command.

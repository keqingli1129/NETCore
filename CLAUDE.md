This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

A .NET 10 solution built on Clean Architecture. The Northwind sample database is the domain. Two web hosts share the same Application/Domain/Infrastructure/SharedKernel layers:

- **CoreWebAPI** — REST API, JWT bearer auth, OpenAPI + Scalar UI. Entry redirect goes to `/scalar/v1`.
- **CoreMVC.Web** — MVC + Razor Pages app with ASP.NET Identity, external auth (SAML, Google, EntraID/OIDC), and Redis caching in production.

Both hosts call a single `AddAppDI`-style composition that wires the layers together (see `Program.cs` and each project's `DependencyInjection.cs`).

## Commands

All commands run from the repo root against `NETCore.sln`.

```bash
dotnet restore ./NETCore.sln
dotnet build ./NETCore.sln -c Release
dotnet test ./NETCore.sln                      # all unit + integration tests

# Run a single test project
dotnet test ./CoreWebAPI.Tests/CoreWebAPI.Tests.csproj

# Run a single test by name (xUnit v3 + VSTest filter syntax)
dotnet test --filter "FullyQualifiedName~AuthControllerTests"
dotnet test --filter "DisplayName~ReturnsToken"

# Run the hosts (Development profile)
dotnet run --project ./CoreWebAPI       # https://localhost:7127, http://localhost:5079
dotnet run --project ./CoreMVC.Web      # https://localhost:7083, http://localhost:5144

# EF Core migrations (DbContext lives in Infrastructure; run with a host as startup)
dotnet ef migrations add <Name> --project ./CoreMVC.Infrastructure --startup-project ./CoreMVC.Web
dotnet ef database update --project ./CoreMVC.Infrastructure --startup-project ./CoreMVC.Web
```

CI (`.github/workflows/coremvc.web.yml`) runs restore → build → test → publish of `CoreMVC.Web` on push to `main`. Azure deploy is currently commented out. `azure-pipelines.yml` exists but its trigger is `none`.

## Architecture and layer boundaries

Dependencies flow inward; the direction matters when deciding where code goes:

```
SharedKernel  ←  CoreMVC.Domain  ←  CoreMVC.Application  ←  CoreMVC.Infrastructure
                                          ↑                          ↑
                                   CoreWebAPI / CoreMVC.Web (hosts compose all layers)
```

- **SharedKernel** — framework-agnostic primitives: `Result`/`Result<T>` (railway-oriented error handling, throws if you read `.Value` on a failure), `Error`/`ErrorType`/`ValidationError`, `Entity` base class with the domain-event list, and the `IDomainEvent`/`IDomainEventHandler` contracts.
- **CoreMVC.Domain** — entities (the Northwind schema), domain events (`Events/`), and the authorization permission catalog (`Authorization/Permissions.cs`). `Order` is a `partial class`: the EF-scaffolded shape is in `Order.cs`, hand-written behavior like `MarkAsShipped` (which raises `OrderShippedEvent`) is in `Order.Domain.cs`. Keep behavior in the `.Domain.cs` partials so it survives re-scaffolding.
- **CoreMVC.Application** — CQRS use cases via **MediatR**. Commands/queries + handlers live under feature folders (e.g. `Orders/Commands`, `Orders/Queries`). Defines the interfaces (`IOrderRepository`, `ICurrentUserService`, `IEmailSender`, `ITokenCacheService`) that Infrastructure implements. Domain-event handlers also live here (`Handlers/`).
- **CoreMVC.Infrastructure** — implementations: `ApplicationDbContext` (EF Core + Identity), repositories, SMTP email, distributed-cache token service, and the `PermissionAuthorizationHandler`.

### Key patterns to follow

- **CQRS via MediatR**: controllers should be thin and dispatch through `IMediator` (`OrdersCqrsController` is the reference). The older `OrdersController` calls a repository directly — prefer the CQRS path for new write/read use cases.
- **Domain events**: mutate an entity through a domain method that calls `Raise(...)`. Events are dispatched **after** `SaveChangesAsync` inside the repository (`OrderRepository.SaveAndDispatchAsync`), then cleared. Don't publish events directly from handlers; raise them on the entity.
- **Permission authorization**: permissions are string constants in `Permissions` (nested static classes). `AddPermissionAuthorization` reflects over them to register a policy per permission. `PermissionAuthorizationHandler` checks for a matching `"permission"` claim. Add a new permission constant *and* protect endpoints with `[Authorize(Policy = Permissions.X.Y)]`.
- **EF scaffolding**: the data model was generated by EF Core Power Tools from Northwind (`CoreMVC.Web/efpt.config.json`). Entity files and the `ApplicationDbContext` partials are auto-generated — treat them as regenerable and put custom logic in separate partial files. `DbContextExtensions.SqlQueryAsync<T>` and `ApplicationDbContextProcedures` support raw SQL / stored-procedure calls.

## Configuration

- **Connection string** `DefaultConnection` (SQL Server) drives EF Core; `Redis` connection string is used only in production for distributed cache (Development uses in-memory).
- **CoreWebAPI** requires `Jwt:Key` (plus `Jwt:Issuer`/`Jwt:Audience`); startup throws if `Jwt:Key` is missing.
- **CoreMVC.Web** external auth is opt-in by configuration presence — Google (`Authentication:Google:*`), EntraID (`Authentication:AzureAd:*`), and SAML (`Saml:*`) are only registered when their settings exist; otherwise startup logs a warning and skips them. Uses `UserSecretsId` for local secrets.

## Testing

- xUnit **v3** with **FluentAssertions**. Mocking uses both **NSubstitute** and **FakeItEasy** (some controllers have parallel `*Tests` and `*TestsUsingFakeItEasy` / `*FakeTests` files demonstrating each).
- Integration tests use `WebApplicationFactory<Program>`. Each host exposes `Program` as a `public partial class` (`ProgramEntry.cs`) solely so the factory can reference it.
- `CustomWebApplicationFactory` swaps SQL Server for the EF Core **InMemory** provider (it must remove both `DbContextOptions<T>` and the EF Core 9+ `IDbContextOptionsConfiguration<T>` registrations to avoid dual-provider conflicts) and installs a `TestAuthHandler` ("Test" scheme) that auto-authenticates requests. Reuse this factory for new API integration tests.
- `CoreMVC.Web.Tests` includes `TestAsyncEnumerable`/`TestAsyncQueryProvider` helpers for mocking async EF Core `IQueryable` queries.
